AIの絵を“縮小版じゃなく原寸”で受け取る関数を9本に配った日🌸

#AI#音#映像#パイプライン

きょうやったこと（ぜんぶ完了ぶんだけ）

AI でショートアニメを作っていると、画像生成 AI（私たちは Gemini を使ってます）に「この絵ちょうだい！」とお願いする場面が山ほどあります。

きょうの作業はこの 2 つ：

  1. 生成した画像を“原寸（フルサイズ）”で受け取る関数を追加して、9 本のスクリプト全部で共通化した
  2. 学習用の素材データ（train_data_v3）を Git の管理対象から外した

どちらも地味だけど、後でめちゃくちゃ効いてくる“土台の掃除”です。順番に、料理に例えながらいきます🍳

アイリス （あわあわ）
お姉ちゃーん！ AI が描いてくれた絵、なんか小さくてボヤけてることない！？ あたしせっかくの神絵がしょぼく見えて泣きそうなんだけど！
ルピナス （ふつう）
あー、それね。AI からもらう画像って、何も指定しないと“プレビュー用の小さい版”が返ってくることがあるの。きょうはそれを“原寸（フルサイズ）でちゃんと受け取る”ようにしたんだよ。
フィオナ （笑顔）
メニュー表に載っている小さな料理写真と、実際にお皿で運ばれてくる料理の違い、と言えば分かりやすいでしょうか。私たちが欲しいのは“運ばれてくる本物”のほうなんです。

学び①：画像生成 API は“原寸 URL”を取りに行く一手間が要る

画像生成 AI から返ってくるデータには、表示確認用の縮小サムネと、ダウンロード用の原寸データが別々に用意されていることがよくあります。

何も考えずに最初に見つかった URL を保存すると、小さい・粗い版を掴んでしまう——これが「なんか画質悪いな？」の正体。

コツ：レスポンスの中から“フルサイズ用のリンク”を選んで取りに行く処理を、専用の関数（download_full_size 的なもの）として用意しておく。こうすると「とりあえず原寸ちょうだい」と一行書くだけで毎回ちゃんと高画質が手に入ります。

アイリス （びっくり）
なるほど〜！ じゃあその“原寸ちょうだい”の魔法、スクリプト全部に書けばいいんだ！ あたし 9 本ぜんぶにコピペしてくる！
フィオナ （呆れ）
アイリスちゃん、待ってください。同じ呪文を 9 か所に書き写すと、あとで直したいとき 9 か所ぜんぶ直さないといけなくなるんですよ……。
ルピナス （ドヤ顔）
そう。だから“魔法そのもの”は 1 か所にまとめて書いて、9 本のスクリプトからは『あの魔法よろしく』って呼ぶだけにしたの。これを共通化って言うんだよ。

学び②：同じ処理は“1 か所にまとめて呼ぶ”（DRY 原則）

プログラミングには DRY（Don't Repeat Yourself＝繰り返すな） という有名な考え方があります。

料理本で言えば、「だしの取り方」を全レシピのページに毎回フルで書くのではなく、巻頭に一度だけ書いて各レシピからは「だし（→ P.3 参照）」と呼ぶイメージ。

メリットはここ：

  • 修正が 1 か所で済む（だしの分量を変えたら全レシピに反映）
  • コピペミスで「6 本目だけ古いまま」みたいな事故が起きない
  • 新しいスクリプトを足すときも、関数を呼ぶだけで同じ品質になる

きょうは「フルサイズ DL 関数」を本体（共通部分）に置いて、9 本のスクリプトがそれを呼ぶ形に揃えました。これで“どのスクリプトから生成しても原寸で揃う”状態になります。

アイリス （笑顔）
コピペ大魔王のあたしには耳が痛い話だけど、たしかにラクだ……！ 1 個直したら全部直るって最高じゃん！
フィオナ （ふつう）
ふふ。ではもう一つの作業、『学習用の素材を Git から外した』ほうも説明しますね。アイリスちゃん、Git って何をする道具か覚えていますか？
アイリス （考え中）
えっと……作業の“やり直しボタン”いっぱい付いたタイムマシン的なやつ！ いつ何を変えたか記録してくれる！
ルピナス （大笑い）
だいたい合ってる（笑）。でね、その記録に“重たい学習素材”まで全部入れちゃうと、タイムマシンがブクブク太って動きが鈍くなるの。だから素材は別管理にしたんだ。

学び③：巨大な“素材データ”は Git に入れない（.gitignore）

Git はファイルの 変更履歴 を残す道具です。文章やコードのような“ちょっとずつ育てるもの”の管理は得意。

でも、AI 学習用の画像素材（私たちの train_data_v3）みたいに 大量・巨大・しょっちゅう差し替わる データを履歴に丸ごと突っ込むと——

  • リポジトリが一気に膨れて、クローン（複製）もプッシュも遅くなる
  • 「絵を 1 枚足しただけ」で履歴がゴチャゴチャになる

対策が .gitignore。冷蔵庫（リポジトリ）に“入れないものリスト”を貼っておくイメージで、train_data_v3 をそこに書いて履歴対象から除外しました。

ポイント：素材は消したわけではなく、別管理にしただけ。コード（レシピ）は Git で、素材（食材）は別の置き場で——と役割を分けるのが、ものづくりを軽く保つコツです。

フィオナ （ウインク）
『変わっていくもの＝Git』『重くて差し替わるもの＝別置き』。この線引きができると、プロジェクトがずっと身軽になりますよ。

まとめ（きょうの有意義ポイント）

  • 画像生成 AI からは“原寸（フルサイズ）”を取りに行く一手間を。最初に拾える URL が縮小サムネのことがある。専用の DL 関数を作っておくと毎回高画質。
  • 同じ処理は 1 か所にまとめて呼ぶ（DRY 原則）。9 本にコピペ→9 か所修正地獄を避けられ、品質も揃う。
  • 巨大・差し替わりの多い学習素材は Git に入れない（.gitignore）。履歴は“育てるコード”用、素材は別置き、と役割分担するとリポジトリが軽いまま。
  • 共通化と分離は“今日のラクより明日のラク”。動いている今こそ土台を整えると、後の自分が救われる。
