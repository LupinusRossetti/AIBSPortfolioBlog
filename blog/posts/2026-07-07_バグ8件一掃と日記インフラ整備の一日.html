1. 🐛 flow-b 直接改修フェーズ：BUGFIX_LOG #1〜#8 全件完了

動画生成ツール flow-b の直接改修フェーズで、事前に洗い出していたバグ8件を全て修正し、コミットまで完了しました。.gitignore の拡充も同時に行っています。

かみ砕くと： バグ修正は「料理レシピの曖昧な表現を直す作業」に似ています。「塩少々」と書いてあるレシピを読んだ料理人が毎回手加減に迷うのと同じように、コードの中に「え、どっちの処理にすればいい？」と迷う箇所があると、ツールは条件次第でおかしな動きをします。8か所の「迷い」を全部「こうする」と断言できるコードに書き直したのが今日の作業です。

技術ディテール： BUGFIX_LOG #1〜#8 は、ファイルパス解決のミス・例外ハンドリングの漏れ・制御フローの不整合・状態変数の初期化タイミングのずれ、といった「動くときは普通に動くが、ある条件が揃うと静かに誤動作する」タイプが中心でした。こういった潜在バグは通常の動作テストでは見逃しやすいため、BUGFIX_LOG として番号を振ったコメントで管理し、「このバグがどのコミットで解消されたか」を後から追跡できる状態を維持しています。.gitignore の拡充は、生成途中の一時ファイルやローカル設定ファイルがリポジトリに紛れ込まないようにする整理で、複数環境で動かす場合の事故防止にもなります。

2. 📋 ブログ日記の『材料切れ』問題と解決策

7/6分の日記が空白になっていたことに今日気づきました。原因は日記生成の材料として使っていた『朝礼まとめ』が止まっていたため、Claude Code 上での自律作業が日記に一切反映されない穴が生まれていたことでした。

かみ砕くと： 会社の日報システムが「朝礼での発表内容」をもとに自動記録する設計になっているとします。ところが朝礼をすっ飛ばしてそのまま仕事を始めると、どんなに大きな成果を出しても日報に一行も残りません——今回の問題はまさにこの状態でした。ツール自体は元気に動いていても、入口が詰まっていれば出力は空になります。

技術ディテール： 対策として blog_material/{date}.md（例：blog_material/2026-07-07.md）という中間ファイルを新設しました。「その日のセッション上で完了した、公開可能な作業を都度メモしておく場所」として機能します。日記生成スクリプトはこのファイルも材料として読み込む形にすることで、朝礼まとめが止まっても個別メモがあれば穴が空かない二重構造になりました。7/6分については、その日の実際の作業（配信分析の資料統合・活動アイデア整理・裏方ツールの追従）をもとに手動で書き起こして補完しています。

4. ✍️ ブログ品質基準のアップデート：『両方ないと不合格』ルール

このブログの品質基準に、今日から新しいルールを加えました。

新ルール：各トピックの解説には、①初心者向けのたとえ話と②AIでものづくりしている人向けの具体的な技術ディテール（固有名詞・数字・手法名など、一般論で終わらない記述）の両方が必須。どちらか片方だけの記事は不合格。

かみ砕くと： 料理番組でたとえると、「プロ向けに高度な技を解説するだけの回」は上手な人には参考になるけど初心者は置いてけぼりになります。逆に「誰でもできる超簡単レシピだけの回」は入門者には優しいけど上手い人には物足りない。「やさしく説明しながら、本格的なコツも伝える」——その両立が、異なる読者層に同時に届く記事の条件です。

技術ディテール： あわせて文字数の上限制限を撤廃しました。「中身が伴うならどこまで長くてもよい、中身が薄ければ短くてよい」というシンプルな方針です。たとえ話・技術ディテール・具体例をそれぞれ1〜2文で切り上げず、読者が『なるほど』と思えるまで書き切ることが品質として定義されます。この変更は今日執筆するこの記事から適用しています。

5. 🖼️ ポートフォリオ・サイト更新まとめ

LupinusPrivate（ポートフォリオ＋ブログサイト）側での主な更新です。

AIイラスト生成ブロックの強化： これまでテキスト説明だけだった部分に、実際に生成したイラストのプレビューを直接埋め込む形に変更しました。「どんなものが作れるか」を読んで理解するのではなく、見て伝わるページになっています。

Nanobanana2 ギャラリー新設 ／ 750 ギャラリーは準備中ゲート付きで先行配置： LoRAなどで生成したイラストを展示するギャラリーページを追加。750 ギャラリーはコンテンツが揃い次第ゲートを外すだけで公開できる状態を先に作ってあります。

かみ砕くと： 「準備中ゲート付きで先に配置」という手法は、建物を建てる前に『2026年秋オープン予定』の看板を立てておくのに似ています。中は空でも外からは「ここに何かができる」と分かります。準備ができたらゲートを外すだけ——コンテンツの完成タイミングと公開タイミングを切り離せる設計です。

技術ディテール： ブログの禁止トピック管理は、記事生成プロンプトの制約リストと既存記事のテンプレート変数・HTML属性の両方を一致させる必要があります。今回、テンプレートエンジンのレンダリング後のHTMLを目視確認したところ、内部カテゴリタグが <meta> 要素と <article> 要素の属性として意図せず露出していた箇所を発見・修正しました。7/6 記事は特定の内容を差し替えて大喜利コーナーへ更新した上で正式公開しています。

6. 📌 今日の有意義ポイント まとめ

  • バグは番号を振って追跡可能にする：BUGFIX_LOG #N 形式で管理すると「このバグがどのコミットで解消されたか」が後から追える。エラーで落ちる派手なバグより、正常終了しながら誤動作する潜在バグの方が発見しにくく危険。
  • 自動化ツールは『入口』が詰まると何も出てこない：ツール本体が動いていても、材料の供給路が途絶えれば出力は空になる。仕組みの外側（材料ファイルの生成）を二重化しておくと穴が空きにくい。
  • blog_material/{date}.md で作業記録を都度保存する：朝礼まとめが止まっても個別メモファイルがあれば日記生成が止まらない。Claude Code セッション上の作業を公開可能な形で残す中間ファイルとして機能させる。
  • 記事品質の合格条件を明確化する：「初心者向けのたとえ話」と「AIでものづくりする人向けの技術ディテール（固有名詞・数字・手法名）」の両方が揃って初めて合格。片方だけでは半分の読者にしか届かない。
  • 文字数より密度が品質：字数制限を撤廃し、中身が伴うなら長くてよい方針に変更。たとえ・技術ディテール・具体例をそれぞれ書き切ることが基準。
  • ギャラリーは『準備中ゲート付きで先に配置』：コンテンツが揃う前に場所を確保しておく。公開時はゲートを外すだけ——段階的な公開をしやすくする設計手法。
