🔢 AI の出力トークン上限を 32000 → 64000 に倍増

動画生成ツール auto_generate.py の設定で、AI に返答させるテキスト量の上限を指定する環境変数 CLAUDE_CODE_MAX_OUTPUT_TOKENS を 32000 から 64000 に引き上げました。

アイリス （考え中）
トークンってよく聞くけど、イマイチ分かんないんだよね。
フィオナ （ふつう）
LLM がテキストを処理するときの『文字の塊』の単位です。日本語だとだいたい漢字 1 文字が 1 トークン、英語なら単語 1〜2 語で 1 トークンくらいのイメージです。
アイリス （びっくり）
じゃあ 32000 って、かなり長い文章じゃない？
ルピナス （呆れ）
そう思うじゃん。でも動画スクリプト全体を一気に生成しようとすると、複数シーンのセリフ＋ナレーション＋演出指示がまとめて出てくるから、長い案件だと余裕でオーバーしてたのよ。

バグの正体と修正のポイント

コードの中で AI への max_tokens パラメータを直打ちせず、環境変数 CLAUDE_CODE_MAX_OUTPUT_TOKENS から読み込む設計になっていました。 この環境変数のデフォルト値が 32000 のままだったことが、長い生成物が途中でぷっつり切れるバグの原因でした。

かみ砕くと： コンビニのレシートプリンターに「最大 30 cm までしか印刷しない」というリミッターがかかっていた状態。長いレシートは途中でぷつっと切れていたわけです。今回それを 60 cm に変更したイメージ。

技術ディテール： Claude API の max_tokens パラメータは、省略するとモデルデフォルト（claude-sonnet-4-6 なら 8192）に戻ります。環境変数で一元管理する設計は複数スクリプト間でパラメータを統一できて便利ですが、デフォルト値が低いまま放置されると今回のように静かに仕様外の挙動が続きます。64000 トークンは日本語にすると約 4.8〜6 万文字相当で、通常の動画スクリプトなら十分な余裕があります。ただし今回の変更が実際に症状を解消するかは次回の生成ランで検証予定です。

アイリス （笑顔）
64000 にしたら絶対大丈夫じゃん！
ルピナス （ドヤ顔）
理論上はね。まだ未検証だからそこはちゃんと保留しとく。
フィオナ （ウインク）
『直した』ではなく『直したはず、次で確認』という姿勢、大事ですよね。

build_blog.py の header() 関数に追記

サイトを自動ビルドする build_blog.py の header() 関数にナビリンクを 1 行追記することで、ビルド対象の全ページのヘッダーが一括更新されます。 ただし stream-info.html だけはビルドスクリプトの自動生成対象外だったため、HTML ファイルを直接手動で修正しました。

かみ砕くと： 全ページのヘッダーを量産するゴム印（スタンプ）の原版に Gallery を彫り直した状態。ビルドを走らせれば全ページ一括で反映されます。ただし 1 枚だけ手書きで作ったページは自分でペンを入れました。

技術ディテール： 静的サイトジェネレーター（Python スクリプト方式）で共通パーツを関数として生成している場合、新しいナビ項目は header() 関数 1 箇所の追記だけで全ページに波及します。例外ページ（自動生成対象外）が存在する場合は手動フォローが必要です。今後の修正漏れを防ぐには、例外ページの一覧を CLAUDE.md や README に明記しておくのが確実です。

ルピナス （大笑い）

なぜ抜けが起きたのか・再発防止

トークコーナーを必須にするルールが記事生成プロンプト（SYSTEM_PROMPT）に追記されていましたが、その更新が実際の生成時に反映されていない状態が続いていました。要は「ルールを書いたけどそのルールで動かしていなかった」というズレです。

かみ砕くと： 新しいチェックリストを印刷したのに、現場ではまだ古いチェックリストを使い続けていた状態。ルールと実運用を定期的に突き合わせる確認が必要でした。

技術ディテール： プロンプトをファイルで管理している場合、ルール変更後に「変更後のプロンプトが実際に読み込まれているか」をワンショット生成でサニティチェックすると、今回のようなズレを早期に発見できます。また、生成物に必須要素（コーナーなど）があれば、出力後に簡単な正規表現チェックを挟むことで機械的に検出できます。プロンプトの運用は『書く』→『適用する』→『確認する』の三段階をセットで回すのが重要です。

アイリス （笑顔）
ルールを書いて満足しちゃいけないんだね。ちゃんと使われてるか確認も大事！
ルピナス （ドヤ顔）
まさに。コードでも習慣でも同じね。書いた≠実行されてる。
フィオナ （ふつう）
CI の自動テストと同じ発想で、生成物を機械的にチェックできる仕組みを入れておくと安心ですね。

まとめ：今日の有意義ポイント

  • AI の出力が途中で切れるバグは max_tokens 上限が原因の可能性大。環境変数で管理している場合はデフォルト値の確認を怠らずに。API レスポンスの finish_reason が 'length' なら上限打ち切りの確定証拠。
  • 環境変数でパラメータを一元管理するパターンは便利だが、デフォルト値の見直しタイミングを意識的に設けること。生成物が長くなる局面（スケールアップ時）で見落としやすい。
  • git 管理に引き継ぎメモ（handoff / INSIGHTS）を含めておくと、AI セッション間の文脈継続が強化される。人間チームの議事録管理と本質は同じ。
  • 静的サイトジェネレーターで共通パーツを関数管理している場合、自動生成対象外の例外ページを CLAUDE.md や README に明記すると修正漏れを防げる。
  • プロンプトのルール変更後は『書く』→『適用する』→『確認する』の三段階をセットで回す。書いた≠使われている。
